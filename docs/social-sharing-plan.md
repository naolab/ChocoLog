# chocoLOG 友人間の記録共有計画（Draft v0.2）

- 作成日: 2026-08-17
- 対象: iOS先行、将来的にAndroid対応
- ステータス: Firebase採用決定・実装前
- 関連資料: [要件定義書](./requirements.md) / [Flutterアーキテクチャ](./architecture.md)

## 1. 目的

自分のトレーニング記録を、招待した友人だけが見られるようにする。公開SNSのような不特定多数との交流ではなく、友人同士で「今日は何をやったか」「最近続けられているか」をゆるく確認できる機能を目指す。

最初からソーシャル機能を大きく広げず、現在の端末保存・オフライン記録を壊さずに、クラウド同期と共有を段階的に追加する。

## 2. 前提と推奨方針

### 2.1 前提

- 現在の記録は端末内のDrift/SQLiteに保存している
- 共有にはユーザー識別とクラウド保存が必要になる
- 友人間の共有を対象とし、不特定多数への公開は対象外とする
- 筋トレの重量・回数・セット、有酸素の時間など、既存の記録単位を再利用する
- 進行中の記録は共有せず、保存済みの完了記録を共有対象とする

### 2.2 推奨する初期仕様

| 項目 | 推奨案 |
|---|---|
| アカウント | 未ログインでも端末保存は利用可能。共有機能ではGoogleログインを必須にし、iOS公開前にSign in with Appleを追加する。パスワード管理は行わない |
| 友人追加 | `CL-7K4P9Q`形式の公開ユーザーIDを基本に、同じ招待情報をコード・リンク・QRで渡す。友人申請は相互承認制 |
| 共有単位 | 友人関係単位。承認後はレポートの履歴にある自分の過去記録をすべて閲覧できる |
| 初期公開範囲 | 友人承認前は非公開。友人関係が成立した時点で履歴共有を開始 |
| 友人の閲覧範囲 | レポートの「履歴」のみ。分析、目標、店舗、メモ、体重などは共有しない |
| 編集権限 | 記録者本人のみ編集・削除可能。友人は閲覧のみ |
| 通知・更新 | 初版はプッシュ通知・Realtime購読を行わず、友人の履歴画面を開いた時または手動更新時に取得 |
| 同期方針 | ローカル優先。通信復帰時に未同期変更を送信 |
| バックエンド | Firebase Spark（Firebase Authentication、Cloud Firestore、Firebase Security Rules）。StorageとCloud Functionsは初版では使わない |

Flutter側はRepositoryの境界越しにFirebase SDKを利用し、画面からFirebase SDKを直接呼ばない。将来サービスを変更できるよう、認証・同期・共有の外部依存を分離する。

## 3. ユーザーストーリー

### 3.1 共有する側

1. Googleでログインする
2. 自分の公開ユーザーIDをコード・リンク・QRで友人へ渡す
3. 友人申請を承認する
4. トレーニングをいつもどおり記録する
5. 友人関係が成立している相手の履歴に、自分のレポート履歴が自動的に表示される
6. 友人解除を行うと、相手の画面から自分の履歴が非表示になる

### 3.2 見る側

1. ユーザーID・リンク・QRから友人申請を送る
2. 相手が申請を承認する
3. レポートの「履歴」から友人を選ぶ
4. 友人の過去を含む履歴を確認する
5. 友人の記録を編集・削除することはできない

### 3.3 失敗・解除時

- 友人申請を拒否・キャンセルできる
- 友人関係を解除できる
- 友人解除後は相手から履歴が見えなくなる
- アカウントを削除すると、クラウド上の本人情報・同期記録を削除し、友人側からも履歴を見えなくする。端末内の記録は残す
- 通信できない場合も、自分の記録は従来どおり端末へ保存できる

## 4. 初版の機能スコープ

### 4.1 初版で実装する機能

- Googleログイン・ログアウト（iOS公開前にSign in with Appleを追加）
- 現在端末にある記録の初回クラウド同期
- 公開ユーザーIDの発行・表示
- ユーザーIDを使った友人申請（コード・リンク・QR）
- 友人申請の承認・拒否・キャンセル
- 友人一覧
- 友人のレポート履歴の閲覧
- 友人関係の解除
- 同期状態（同期済み、未同期、失敗）の表示
- 通信失敗時の再送
- アカウント削除

### 4.2 初版では実装しない機能

- 不特定多数への公開タイムライン
- いいね、コメント、リアクション
- 友人の自動フォロー
- 友人の位置情報・現在店舗・リアルタイム在館情報
- 進行中トレーニングのリアルタイム共有
- 友人記録の複製、編集、削除
- 友人記録の分析・目標達成状況の共有
- 体重・体脂肪・写真の共有
- 友人へのプッシュ通知
- Web版、管理画面、公開プロフィール検索

## 5. 共有するデータ

### 5.1 初期表示する項目

友人に表示する内容は、現在のアプリの「レポート > 履歴」に表示しているカードを基本的にそのまま再利用する。

- 記録日
- 器具画像・器具名
- 筋トレのセット数、回数、重量
- 有酸素の運動時間

### 5.2 初期状態で共有しない項目

- 正確な開始時刻
- 店舗名・店舗位置
- メモ
- 体重、体脂肪率、写真
- 端末ID、メールアドレスなどのアカウント情報
- 進行中セッションの状態

初版では個別の共有確認画面を設けず、友人関係の成立を共有開始の条件とする。店舗やメモを将来共有可能にする場合も、初期値は非共有とする。

## 6. データモデル案

現在のローカルモデルを維持しつつ、同期用ID・所有者・更新情報を追加する。

### 6.1 追加する概念

```text
users
public_ids
friend_requests
friendships
sync_records
workout_sessions
```

### 6.2 主なフィールド

#### users

- `id`: Firebase AuthenticationのUID
- `public_id`: `CL-7K4P9Q`形式の公開ユーザーID
- `display_name`: 友人に表示する名前
- `avatar_url`: 初版では任意。未設定ならイニシャル表示
- `created_at`, `updated_at`

#### public_ids

- `public_id`: 完全一致検索用の公開ID
- `user_id`: Firebase AuthenticationのUID

公開IDは認証情報ではなく、友人申請の宛先を特定するためだけに使う。

#### friend_requests

- `id`
- `requester_id`, `target_id`
- `status`: `pending` / `accepted` / `rejected` / `cancelled`
- `created_at`, `updated_at`, `expires_at`

#### friendships

- `id`
- `requester_id`, `addressee_id`
- `status`: `accepted` / `blocked`
- `created_at`, `updated_at`

#### workout_sessions

- `id`: ローカル記録と対応する同期ID
- `owner_id`: Firebase AuthenticationのUID
- `recorded_date`
- `updated_at`, `deleted_at`
- 既存の器具・セット・有酸素記録を履歴表示に必要な形で保持

友人関係が`accepted`の場合、`owner_id`が友人のセッションを読み取れる。セッション単位の共有許可コレクションは作らない。

#### sync_records

- `local_id`
- `remote_id`
- `entity_type`
- `operation`: `upsert` / `delete`
- `version`または`updated_at`
- `sync_status`: `pending` / `synced` / `failed`
- `last_error`

ローカルのセッション・種目・セットには、将来的な同期を見越して`remoteId`、`ownerId`、`updatedAt`、`deletedAt`を追加する。既存の端末内IDは移行後も保持し、初回同期時に対応表を作る。

## 7. 同期と競合解決

### 7.1 基本フロー

```text
ローカル保存
    ↓
未同期キューへ追加
    ↓ 通信可能時
Firebase認証トークン確認
    ↓
サーバーへupsert / delete
    ↓
同期済みへ更新
```

- セット追加・編集・削除は、現在どおり先にローカルへ保存する
- 同期失敗で記録入力をブロックしない
- アプリ起動時、復帰時、手動更新時に同期を試みる
- 同じ記録を複数端末で編集した場合は、`updatedAt`とバージョンで競合を検出する
- 初版は「最後に保存された変更を優先」を基本とし、競合が発生したことをユーザーへ表示する
- 友人側は履歴を読み取り専用で閲覧し、本人だけが記録を編集・削除できる
- 削除は即時物理削除ではなく、一定期間`deletedAt`を保持して同期する

### 7.2 初回移行

- 未ログインの既存ユーザーは、これまでどおりローカルのみで利用できる
- ログイン後に「この端末の記録を同期しますか？」を表示する
- 初回は既存記録をクラウドへコピーするが、共有状態はすべて非公開にする
- 同期失敗時も、ローカル記録は削除しない
- ログアウト時も端末内記録は削除しない。共有データの再表示には再ログインが必要

## 8. 画面追加・変更案

### 8.1 設定

- アカウント
  - ログイン状態
  - 表示名
  - ログアウト
  - アカウント削除
- 友人と共有
  - 友人一覧
  - 自分の公開ユーザーID
  - コード・リンク・QRで友人を追加
  - 友人申請の確認
- 同期状態
  - 最終同期日時
  - 未同期件数
  - 今すぐ同期

### 8.2 友人一覧

- 友人名
- 最終共有日
- 友人関係の解除
- 共有記録一覧への遷移

### 8.3 友人履歴表示

- 初版では個別の共有確認シートを設けない
- 友人承認後、レポートの履歴から友人の記録を表示する

### 8.4 レポート・履歴

- 自分の記録と友人の記録を混ぜない
- 初版は「自分」「友人」の切り替えを履歴画面に置く
- 「友人」を選択した場合は、友人一覧から表示対象を選ぶ
- 共有記録には友人名と共有アイコンを表示する
- 友人の記録から自分の記録を直接編集する導線は作らない

## 9. 権限・プライバシー・安全性

- 友人承認前の履歴は常に非公開
- 友人追加は相互承認した場合のみ成立する
- 公開ユーザーIDは認証情報として扱わず、完全一致検索の宛先に限定する
- Firebase Security Rulesで、本人または`accepted`状態の友人だけが履歴を読めるようにする
- クライアントから他人の`owner_id`を指定して取得できないようにする
- 退会・友人解除時の表示反映を定義する
- アプリ内に「この履歴は承認済みの友人だけに見えます」「公開SNSには表示されません」と明示する
- 利用規約、プライバシーポリシー、アカウント削除フローを一般公開前に整備する
- chocoZAPの公式サービスや会員情報とは連携しない

### Phase 1: 同期基盤

- レポート履歴の「自分」「友人」切り替え

## 11. テスト計画

### 11.1 単体テスト

- 公開ユーザーIDの生成・重複防止
- 友人申請の生成・期限切れ・承認・拒否・キャンセル
- 友人関係の状態遷移
- 友人関係に基づく履歴閲覧権限の判定
- 初回同期のID対応表
- 未同期キューの再送と冪等性
- 競合検出

### 11.2 Widgetテスト

- 未ログイン時に端末保存が利用できる
- ログイン後に初回同期確認が表示される
- 招待承認・拒否が画面に反映される
- 友人の履歴に不要な情報が表示されない
- 友人解除後に友人側から見えなくなる
- 同期失敗時も記録入力を続けられる

### 11.3 受け入れ基準

- 友人以外から共有記録を取得できない
- 記録追加・編集・削除がオフラインでも従来どおり動く
- 承認済みの友人に過去履歴を含む履歴が表示される
- 友人解除が双方の画面に反映される
- ログアウトしても端末内の自分の記録が消えない
- アカウント削除時の共有記録の扱いが仕様どおりになる
- `flutter analyze`と既存テストが通過する

## 12. 未決事項・次に決めること

実装開始前に、次の細部を決める。主要な共有方針とFirebase採用は確定済みとする。

1. 表示名を必須にするか（初版は必須を推奨）
2. 公開ユーザーIDを変更・再発行できるようにするか（初版は固定を推奨）
3. 友人申請の有効期限（初版は7日を推奨）
4. 友人解除後に再追加した場合も過去履歴を再表示するか（再表示を推奨）
5. ブロック・通報機能をいつ追加するか（初版では後回し）
6. 一般公開前に必要な利用規約・プライバシーポリシー・問い合わせ窓口

### 初期判断の推奨

初版は、**相互承認した友人に、レポートの履歴を過去分も含めて自動共有する**仕様とする。履歴には記録日・器具画像・器具名・重量・回数・セット数・有酸素時間を表示し、分析・目標・店舗名・メモ・体重・正確な時刻は共有しない。ローカル保存を基本とし、友人の履歴画面を開いたときまたは手動更新時にFirestoreから最新情報を取得する。
