# chocoLOG 友人間の記録共有計画（Draft v0.1）

- 作成日: 2026-08-17
- 対象: iOS先行、将来的にAndroid対応
- ステータス: 計画段階
- 関連資料: [要件定義書](./requirements.md) / [Flutterアーキテクチャ](./architecture.md)

## 1. 目的

自分のトレーニング記録を、招待した友人だけが見られるようにする。公開SNSのような不特定多数との交流ではなく、友人同士で「今日は何をやったか」「最近続けられているか」をゆるく確認できる機能を目指す。

最初からソーシャル機能を大きく広げず、現在の端末保存・オフライン記録を壊さずに、クラウド同期と共有を段階的に追加する。

## 2. 前提と推奨方針

### 2.1 前提

- 現在の記録は端末内のDrift/SQLiteに保存している
- 共有にはユーザー識別とクラウド保存が必要になる
- 友人間の共有を対象とし、不特定多数への公開は対象外とする
- 筋トレの重量・回数・セット、有酸素の時間など、既存の記録単位を再利用する
- 進行中の記録は共有せず、保存済みの完了記録を共有対象とする

### 2.2 推奨する初期仕様

| 項目 | 推奨案 |
|---|---|
| アカウント | メールリンク認証またはSign in with Appleを優先。パスワード管理は行わない |
| 友人追加 | 招待リンクまたは6桁コード。検索で知らない人を探す機能は作らない |
| 共有単位 | 完了したトレーニングセッション単位 |
| 初期公開範囲 | 初期状態は非共有。ユーザーが友人またはセッションごとに明示的に共有 |
| 友人の閲覧範囲 | 共有を許可したセッションのみ。過去記録を一括公開しない |
| 編集権限 | 記録者本人のみ編集・削除可能。友人は閲覧のみ |
| 通知 | 初版はアプリ内表示のみ。プッシュ通知は次期候補 |
| 同期方針 | ローカル優先。通信復帰時に未同期変更を送信 |
| バックエンド候補 | Supabase（Auth、Postgres、Storage不要で開始、Row Level Securityを利用） |

Supabaseを採用する場合でも、Flutter側はRepositoryの境界越しに利用し、画面からSupabase SDKを直接呼ばない。将来サービスを変更できるよう、認証・同期・共有の外部依存を分離する。

## 3. ユーザーストーリー

### 3.1 共有する側

1. アカウントを作成またはログインする
2. 友人を招待リンクまたはコードで追加する
3. トレーニングをいつもどおり記録する
4. 完了画面または履歴から「友人に共有」を選ぶ
5. 共有する友人と、表示する情報を確認して共有する
6. 共有を取り消した場合、相手の一覧から非表示になる

### 3.2 見る側

1. 招待を承認する
2. 友人一覧から相手を選ぶ
3. 共有された日付・器具・セット数・時間を確認する
4. 友人の記録を編集・削除することはできない

### 3.3 失敗・解除時

- 招待を拒否できる
- 友人関係を解除できる
- 共有を個別に取り消せる
- アカウントを削除すると、共有先でも本人の共有記録を削除または匿名化する
- 通信できない場合も、自分の記録は従来どおり端末へ保存できる

## 4. 初版の機能スコープ

### 4.1 初版で実装する機能

- アカウント登録・ログイン・ログアウト
- 現在端末にある記録の初回クラウド同期
- 友人招待リンク／招待コードの発行
- 招待の承認・拒否
- 友人一覧
- 完了済みセッションの個別共有
- 共有済みセッションの閲覧
- 共有の取り消し
- 友人関係の解除
- 同期状態（同期済み、未同期、失敗）の表示
- 通信失敗時の再送
- 自分の記録を非公開へ戻す設定

### 4.2 初版では実装しない機能

- 不特定多数への公開タイムライン
- いいね、コメント、リアクション
- 友人の自動フォロー
- 友人の位置情報・現在店舗・リアルタイム在館情報
- 進行中トレーニングのリアルタイム共有
- 友人記録の複製、編集、削除
- 体重・体脂肪・写真の共有
- 友人へのプッシュ通知
- Web版、管理画面、公開プロフィール検索

## 5. 共有するデータ

### 5.1 初期表示する項目

- 記録日
- トレーニング全体の概要
- 器具名
- 筋トレのセット数、回数、重量
- 有酸素の運動時間
- ユーザーが任意で設定したメモ（共有画面で選択した場合のみ。初期値は非共有）

### 5.2 初期状態で共有しない項目

- 正確な開始時刻
- 店舗名・店舗位置
- 体重、体脂肪率、写真
- 端末ID、メールアドレスなどのアカウント情報
- 進行中セッションの状態

共有画面では、共有対象の項目を確認できるようにする。店舗やメモを将来共有可能にする場合も、設定の初期値はオフにする。

## 6. データモデル案

現在のローカルモデルを維持しつつ、同期用ID・所有者・更新情報を追加する。

### 6.1 追加する概念

```text
users
friendships
friend_invites
sync_records
shared_sessions
```

### 6.2 主なフィールド

#### users

- `id`: サーバー側のユーザーID
- `display_name`: 友人に表示する名前
- `avatar_url`: 初版では任意。未設定ならイニシャル表示
- `created_at`, `updated_at`

#### friendships

- `id`
- `requester_id`, `addressee_id`
- `status`: `pending` / `accepted` / `rejected` / `blocked`
- `created_at`, `updated_at`

#### friend_invites

- `id`
- `inviter_id`
- `token_hash`: 招待URLへ生のトークンを保存しない
- `expires_at`
- `max_uses`、`used_at`

#### shared_sessions

- `id`
- `session_id`: ローカル記録と対応する同期ID
- `owner_id`
- `shared_with_id`
- `visibility`: 初版は `friend`
- `include_note`, `include_studio`: 初期値は`false`
- `shared_at`, `revoked_at`

#### sync_records

- `local_id`
- `remote_id`
- `entity_type`
- `operation`: `upsert` / `delete`
- `version`または`updated_at`
- `sync_status`: `pending` / `synced` / `failed`
- `last_error`

ローカルのセッション・種目・セットには、将来的な同期を見越して`remoteId`、`ownerId`、`updatedAt`、`deletedAt`を追加する。既存の端末内IDは移行後も保持し、初回同期時に対応表を作る。

## 7. 同期と競合解決

### 7.1 基本フロー

```text
ローカル保存
    ↓
未同期キューへ追加
    ↓ 通信可能時
認証トークン確認
    ↓
サーバーへupsert / delete
    ↓
同期済みへ更新
```

- セット追加・編集・削除は、現在どおり先にローカルへ保存する
- 同期失敗で記録入力をブロックしない
- アプリ起動時、復帰時、手動更新時に同期を試みる
- 同じ記録を複数端末で編集した場合は、`updatedAt`とバージョンで競合を検出する
- 初版は「最後に保存された変更を優先」を基本とし、競合が発生したことをユーザーへ表示する
- 完了セッションは、友人側に公開された後も本人だけが編集・削除できる
- 削除は即時物理削除ではなく、一定期間`deletedAt`を保持して同期する

### 7.2 初回移行

- 未ログインの既存ユーザーは、これまでどおりローカルのみで利用できる
- ログイン後に「この端末の記録を同期しますか？」を表示する
- 初回は既存記録をクラウドへコピーするが、共有状態はすべて非公開にする
- 同期失敗時も、ローカル記録は削除しない
- ログアウト時も端末内記録は削除しない。共有データの再表示には再ログインが必要

## 8. 画面追加・変更案

### 8.1 設定

- アカウント
  - ログイン状態
  - 表示名
  - ログアウト
  - アカウント削除
- 友人と共有
  - 友人一覧
  - 招待する
  - 招待を確認
  - 共有設定
- 同期状態
  - 最終同期日時
  - 未同期件数
  - 今すぐ同期

### 8.2 友人一覧

- 友人名
- 最終共有日
- 友人関係の解除
- 共有記録一覧への遷移

### 8.3 共有確認シート

- 共有先の友人名
- 記録日
- 器具名と記録内容
- 共有しない項目の説明
- 「この友人に共有する」
- キャンセル

### 8.4 レポート・履歴

- 自分の記録と友人の記録を混ぜない
- 初版は「自分」「友人」の切り替えを友人一覧の配下に置く
- 共有記録には友人名と共有アイコンを表示する
- 友人の記録から自分の記録を直接編集する導線は作らない

## 9. 権限・プライバシー・安全性

- 共有の初期値は常に非公開
- 共有は友人単位またはセッション単位で明示する
- 友人追加は招待を承認した場合のみ成立する
- 招待コードは期限付き・使い捨てにする
- サーバー側のRow Level Securityで、本人または明示的な共有先だけが読めるようにする
- クライアントから他人の`owner_id`を指定して取得できないようにする
- 退会・友人解除・共有取消時の表示反映を定義する
- アプリ内に「この共有は友人だけに見えます」「公開SNSには表示されません」と明示する
- 利用規約、プライバシーポリシー、アカウント削除フローを一般公開前に整備する
- chocoZAPの公式サービスや会員情報とは連携しない

## 10. 実装フェーズ

### Phase 0: 仕様確定

- 共有する情報と共有しない情報を確定
- 友人追加方法を確定（招待リンク＋コードを推奨）
- アカウント削除・友人解除・共有取消の挙動を確定
- バックエンド候補と料金・リージョン・利用規約を確認

### Phase 1: 同期基盤

- 認証画面とセッション管理
- `remoteId`、同期日時、削除フラグのローカルDBマイグレーション
- Supabase接続層とRepositoryインターフェース
- 初回同期、未同期キュー、再送、ログアウト
- 同期状態の表示

### Phase 2: 友人関係

- ユーザープロフィール（表示名のみ）
- 招待リンク／コード
- 招待承認・拒否
- 友人一覧・解除
- Row Level Securityと権限テスト

### Phase 3: セッション共有

- 完了記録の共有確認シート
- 共有先の保存・取消
- 友人側の共有記録一覧・詳細
- 共有済み表示、空状態、エラー・再読み込み

### Phase 4: ベータ検証

- 自分・知人でTestFlightテスト
- オフライン記録→復帰同期
- 同一アカウントの複数端末
- 友人解除・共有取消・アカウント削除
- 通信失敗、認証期限切れ、重複招待、時刻ずれ

### Phase 5: 次期拡張

- 共有範囲の一括設定
- 友人の活動サマリー
- リアクション・コメント（要望があれば）
- プッシュ通知
- 体重などの項目別共有設定
- Android対応

## 11. テスト計画

### 11.1 単体テスト

- 招待コードの生成・期限切れ・使用済み判定
- 友人関係の状態遷移
- 共有権限の判定
- 初回同期のID対応表
- 未同期キューの再送と冪等性
- 競合検出

### 11.2 Widgetテスト

- 未ログイン時に端末保存が利用できる
- ログイン後に初回同期確認が表示される
- 招待承認・拒否が画面に反映される
- 共有確認シートに不要な情報が表示されない
- 共有取消後に友人側から見えなくなる
- 同期失敗時も記録入力を続けられる

### 11.3 受け入れ基準

- 友人以外から共有記録を取得できない
- 記録追加・編集・削除がオフラインでも従来どおり動く
- 共有したセッションだけが友人に表示される
- 共有取消が双方の画面に反映される
- ログアウトしても端末内の自分の記録が消えない
- アカウント削除時の共有記録の扱いが仕様どおりになる
- `flutter analyze`と既存テストが通過する

## 12. 未決事項・次に決めること

実装開始前に、次の項目を決める。

1. 友人には「個別セッション」だけ共有するか、「その日のまとめ」も共有するか
2. 重量・回数・セット数を友人へ常に表示するか、項目ごとに非表示にできるか
3. 店舗名を共有対象に含めるか
4. 表示名の変更と重複をどう扱うか
5. 友人解除時に過去の共有記録を消すか、共有済みのまま残すか
6. アカウントを作らず、招待を受けた人が閲覧専用で見られる方式が必要か
7. バックエンドをSupabaseで確定するか
8. 一般公開前に必要な利用規約・プライバシーポリシー・問い合わせ窓口

### 初期判断の推奨

迷った場合は、**個別の完了セッションを、招待済みの友人へ、重量・回数・セット数・時間だけ共有する**仕様から始める。店舗名・メモ・体重・リアルタイム状態は初版では共有しない。この範囲なら、既存の記録モデルを活かしながら、プライバシーと実装コストを抑えて価値検証できる。
